# 缺陷审计修复

缺陷清单与证据见 [Roadmap · 2026-10-20 缺陷审计](../../../product/roadmap.md#2026-10-20-缺陷审计)。[^roadmap] 本计划只安排落点、顺序和验收。

## Context

- 2026-10-20 对 `main` 的审计记下约六十项缺陷，其中九项高危；十项已在本机用临时测试复现，测试没有提交。现有测试全部通过，说明这些路径都没有覆盖。
- 高危项集中在三处：认证缺省是放开、上游调用没有边界、后台刷新与管理写入互相覆盖。逐项见 Roadmap 该节的表格。
- 与其他计划的关系：
  - [开源就绪与首次发布](../10-10/w0-00-开源就绪与首次发布.md) 只剩打 tag 与真实 OAuth 上游验收。阶段一是否要求在打 tag 前合入，见下方「待确认」第 1 条。
  - [多租户数据面](../10-10/w1-02-多租户数据面.md) 的「配置以数据库为准」与本计划 PR12 重叠。PR12 先做单进程内的「事务落库后再替换」和配置版本号，多租户计划在此之上做多副本重新加载。
  - [身份服务与管理员登录](../10-10/w0-01-身份服务与管理员登录.md) 引入只读角色后，admin 写权限不再等同于网关所有者，PR5 的 secret 引用边界要先于它合入。
  - [下游 MCP OAuth](../10-10/w1-03-下游-mcp-oauth.md) 的「key 删除或吊销后 token 随即失效」沿用 PR1 改过的吊销语义。

## Approach

- 每个 PR 先写失败的回归测试，复现审计记录的场景；修复后反转断言。不为了变绿删除或跳过测试。
- 阶段一修安全缺省，各 PR 可以并行，只有 PR2 的开放模式 Host 规则依赖 PR1 的显式认证模式。
- 阶段二与阶段一并行：PR7 先于 PR8，PR9、PR10 独立。
- 阶段三排在 PR8 之后，因为 PR11 与 PR8 都改 `McpServerRegistry` 的刷新路径。
- 阶段四、五的 PR 互相独立；PR18 改动面最广，放在阶段四最后。阶段六的 PR21 依赖 PR12 的配置版本号，PR22 依赖 PR4 的 URL 编码规则。
- 破坏性变更（认证缺省、`?key=`、`{+name}`、`/config` 收窄、Origin 缺省拒绝）按 [后向兼容策略](../../../architecture/compatibility-policy.md) 在 `CHANGELOG.md` 以「**破坏性变更**」开头，并写明迁移方法。[^compat]
- 改协议、配置、错误码或 admin DTO 的 PR，同时更新对应概念文档、`schemas/admin.json` 与前端生成类型（`just api types`）。新增依赖前先更新 [Crate 选型矩阵](../../../architecture/crate-selection.md)。[^crates]

## 待确认

下列行为变更需要维护者先定，结论写进 Roadmap [产品决策](../../../product/roadmap.md#产品决策)：

1. 阶段一（PR1–PR6）是否列入 Phase 11 准出，在首次打 tag 前合入。建议是，并且 PR7、PR9 一并合入。
2. 认证缺省改为 `required`；开放模式必须显式开启，并绑定一个具名 key；legacy `?key=` 缺省关闭，只对显式标记的 key 开启，并标记弃用；吊销后 key 不可用（PR1）。
3. 带 `Origin` 且不在白名单的 `/mcp` 与 `/v1/*` 请求一律拒绝；开放模式下 Host 只认 loopback；compose 不再内置 admin token 缺省值（PR2）。
4. 需要原样拼接的路径参数改写为 `{+name}`（RFC 6570 reserved expansion），其余一律编码。依赖原样拼接的现有配置需要修改（PR4）。
5. 代理侧的 `/config` 只返回调用方自己的 key 与 scope 内资源，不再返回 `base_url`；`asl__status` 只给可见范围内的计数（PR2）。
6. 上游 4xx 是否向代理返回清洗后的错误摘要。这会把 [错误模型](../../../architecture/error-model.md) 的「用户可见错误不含原始上游响应体」改为「可以包含截断、脱敏后的 4xx 摘要」（PR6）。[^errors]
7. 发现类调用（`tools/list`、`/v1/tools`、`asl__search` 等）计入 key 的 rps/rpm，还是另设限额（PR17）。
8. integrity 基线与隔离集合落库，并新增隔离列表与批准接口（PR14）。

## Reuse

- `swap_config_and_catalog`（`src/admin/crud.rs`）仍是配置替换的唯一入口，`AppState.admin_write` 仍是本进程的管理写锁。PR12 在这两者之上改为「先落库后替换」和增量重建，不另起一套写入路径。
- `LimitRegistry::admit` 与 `CallQuotaGuard` 是唯一的准入与退还入口；发现类限流与拒绝事件都接在它们上面。
- 出站校验复用 `egress::guarded_client` 与 `check_url`；新增的超时、大小上限与 `no_proxy` 都加在这个构造函数上。
- 远程 MCP 超时用 rmcp 原生的 `send_request_with_option` 与 `PeerRequestOptions::with_timeout`，不手写 JSON-RPC。
- 脱敏复用 `observability::redaction` 与 `capture` 的规则，另加「按本次实际注入的凭据值精确替换」。
- SQLite 用 sqlx 的 `SqliteConnectOptions` 与 `SqlitePoolOptions` 显式配置，不新增存储依赖；Retry-After 的 HTTP-date 用 `chrono` 解析，不新增 crate。
- 回归测试复用 `tests/it/support/` 与现有测试里的假上游：`RemoteMcpPeer` 的假实现、wiremock、本机 TCP 监听。

## 阶段一：安全缺省与暴露面

### PR1 gateway key 认证缺省拒绝

- [ ] 先写失败的回归测试：
  - 吊销唯一一枚 token 后，匿名 `/mcp` 与 `?key=<id>` 都返回 401；
  - 配置里只有无 token 的 key 时，匿名 `/mcp` 返回 401；
  - YAML 定义的 key 在线签发 token 后重启，token 仍然有效；
  - 从 YAML 删掉这个 key 并重启后，它不再出现。
- [ ] 认证模式改为显式配置，缺省 `required`（字段名在本 PR 定稿并写进 [配置 Schema](../../../runtime/config-schema.md)，暂定 `gateway_auth.mode: required | open`）。`GatewayAuth::mcp_auth_required` 只读这个配置，不再由「是否还有 token key」推导（待确认第 2 条）。
- [ ] 开放模式必须指定 `anonymous_key`，匿名请求绑定这个 key 的 scope、限额与归属。删除 `mcp_default_key` 的 `.*` 全放行。
- [ ] legacy `?key=` 缺省关闭，只对显式标记的 key 生效，启动时告警。吊销（`DELETE /admin/proxy-keys/{id}/token`）后 key 处于无凭据状态，任何呈现方式都无法认证。
- [ ] YAML 定义的 key 在线签发的凭据写进单独的表（暂定 `proxy_key_credentials`），合并时只对 YAML 里仍然存在的 id 生效；`upsert_proxy_key_db` 不再为 YAML key 插入整行。
  - 迁移：被 YAML 遮蔽、带摘要的旧行，把摘要搬进新表后删除该行；
  - 启动时清理孤儿凭据并告警。
- [ ] `/admin/health` 返回当前认证模式。控制台总览显示这个模式；吊销与删除的确认框写明后果；legacy 徽标改为警示色。
- [ ] `run.yaml`、`deploy/k8s/config.yaml` 与快速上手改为先签发 token 再接入代理。
- [ ] 同步文档：[配置持久化闭环 · K1](../../../runtime/key-credentials-and-persistence.md#k1-proxy-key-凭据化)、根 README 两版、[错误模型](../../../architecture/error-model.md)，并在 `CHANGELOG.md` 记为破坏性变更、写明迁移方法。[^persistence]

验收：
- 回归测试修复前失败、修复后通过；
- README 的「换掉或吊销这枚 key，这个代理的范围就随之消失」成立；
- 只用 token 的现有部署行为不变。

### PR2 收窄代理可见信息与浏览器攻击面

- [ ] 先写失败的回归测试：
  - 持 token 的 key 调 `/config`，看不到其他 key，也看不到范围外的资源；
  - 带外来 `Origin` 的 `/mcp` 与 `/v1/tools` 请求返回 403；
  - 开放模式下，外来 `Host` 的 `/mcp` 请求被拒。
- [ ] `/config` 只返回调用方自己的 key，以及 scope 内资源的 id、domain、provider 与 description，不再返回 `base_url`（待确认第 5 条）。
- [ ] `/metrics` 支持 admin token 认证或独立监听地址，二选一，在本 PR 内定。Ingress 示例显式挡住 `/metrics`，同步 [线上部署](../../../admin/deployment.md)。
- [ ] 新增 `http.allowed_origins`：`/mcp` 与 `/v1/*` 上带 `Origin` 且不在白名单的请求返回 403。开放模式下 `/mcp` 的 Host 白名单缺省为 loopback；required 模式保持现在的不限 Host（待确认第 3 条）。
- [ ] `compose.yaml` 与 `.env.schema` 不再内置 admin token 缺省值，未设置时 compose 报错退出；快速上手改为先 export。
- [ ] `asl__status` 的 provider 计数包含 MCP server，计数只覆盖可见范围。隔离检查移到 scope 校验之后，范围外的工具无论是否被隔离，都返回同一个错误。
- [ ] `/mcp` 遵守 `http.max_body_bytes`，与 [配置 Schema](../../../runtime/config-schema.md) 的说法一致。

验收：
- 回归测试通过；
- 不带 `Origin` 的非浏览器 MCP 客户端行为不变；
- 控制台经 Nginx 同源访问 `/admin` 不受影响。

### PR3 范围规则校验与预编译

- [ ] 先写失败的回归测试：
  - `allowed_tools: ['^search__(?:tavily|exa)__']` 能正常判权；
  - `[unclosed` 在加载和 admin 写入时都被拒；
  - 两条同 id 的 key 启动失败；

- [ ] 控制台的 allow/deny 正则改为一行一条，不再按逗号拆分；正则是否合法以后端的 Rust regex 为准。

### PR6 上游错误收口

- [ ] 同步 [错误模型](../../../architecture/error-model.md) 与 [MCP 治理](../../../runtime/mcp-governance-and-key-limits.md) 中 `last_error` 的口径。[^governance]

## 阶段二：上游调用边界

### PR7 远程 MCP 请求超时

- [ ] 先写失败的回归测试：
  - 只接受 TCP、从不响应的上游，`connect_all` 在超时内返回并把它标为 `unreachable`；
  - `tools/call` 在超时内返回超时错误；
  - 无限返回 `nextCursor` 的上游被分页上限截断。
