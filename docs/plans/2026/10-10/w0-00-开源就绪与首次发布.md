# 开源就绪与首次发布

范围与准出见 [Roadmap · Phase 11](../../../product/roadmap.md#phase-11开源就绪)。[^roadmap] 并发写入问题的证据见 [开源版与 SaaS 双形态 · 前置条件](../../../architecture/open-source-and-saas.md#前置条件)。[^saas] 本计划只安排落点、顺序和验收。

## Context

控制台界面整理已在 2026-10-10 交付。Phase 11 的其余各项都还没做：

- 管理写接口在「读快照 → 修改 → 整体替换」之间没有锁，并发时后完成的写入覆盖先完成的。开源版同样受影响，[多租户数据面](w1-02-多租户数据面.md) 也以它为前提。
- 独立控制台没有上游 OAuth 的「授权 / 撤销授权」和 OAuth 字段编辑（[Admin Console · 分阶段路线](../../../admin/admin-console.md#分阶段路线) 的 C7），`CHANGELOG.md` 的 Unreleased 却写了这项。[^console]
- `release.yml` 只发布网关的二进制和镜像，控制台没有可下载的产物，外部用户只能从源码构建控制台。流水线还没有真实跑过。
- 上游 OAuth 只用进程内模拟授权服务器验证过，Phase 8 准出还差一个真实上游。
- 没有 K8s 部署物；控制台和入口文档只有中文；贡献者签署方式未定。
- 整理控制台时记下的收尾项：代理密钥表单的服务与工具多选仍是原生 `select`；`web/src/components/pending-page.tsx` 早已没有引用；表格展开行在窄屏上的可读性没有检查。

## Approach

PR1 先做：它修的是会丢数据的缺陷，也是多租户计划的前置条件。PR2 要在打 tag 之前合入，否则 CHANGELOG 里有一条不实记录。PR3、PR4、PR5 互不依赖，可以并行。PR6 发布排在 PR1、PR2 之后。PR7 需要维护者在真实上游上完成授权，可以与其他 PR 并行。PR8 由维护者决定，最好在公开接受外部贡献之前定下。

## Files

- `src/http/state.rs`、`src/admin/{crud,mcp,tokens,metadata}.rs`、`src/http/lifecycle.rs` — 管理写锁与持锁范围。
- `tests/it/admin_contracts.rs` — 并发写入回归测试。
- `web/src/features/mcp/{write.ts,server-form.tsx,server-table.tsx}` — OAuth 授权入口与字段编辑。
- `web/src/features/proxy-keys/proxy-key-form.tsx`、`web/src/components/pending-page.tsx`、`web/src/styles.css` — 控制台收尾。
- `web/src/app/`、`web/src/features/`、`web/README.md` — 文案抽取、语言切换与新依赖说明。
- `deploy/k8s/`（新增）、`docs/admin/deployment.md` — K8s 部署物与说明。
- `.github/workflows/release.yml`、`docs/engineering/release-process.md`、`compose.yaml`、`CHANGELOG.md`、`README.md`、`README.zh-CN.md` — 控制台镜像、首个版本与快速上手。
- `CONTRIBUTING.md`、`CONTRIBUTING.zh-CN.md` — 贡献者签署方式。

## Reuse

- `swap_config_and_catalog`（`src/admin/crud.rs`）已经是所有配置写入的唯一替换点。锁加在调用它的写路径上，不另起一套写入入口。
- C7 的 HTTP 契约和服务视图的 `oauth` 段（`grant`、`status`、`expires_at`、`client_id`、`client_secret_ref`、`scopes`）已经在 `schemas/admin.json` 与生成类型里，前端不手写接口类型。
- 控制台已有的确认对话框、`choose()`、行内错误提示和 Kumo 组件；多选改用 Kumo Combobox 的 `multiple`。
- `web/Dockerfile` 与 `just web deploy-smoke` 已经能构建并演练控制台镜像；`release.yml` 现有的镜像 job 是控制台镜像的模板。
- `compose.yaml` 的服务划分、端口与卷是 K8s 清单的对照。

## PR1 并发管理写入串行化

- [x] 先写失败的回归测试：在 `tests/it/admin_contracts.rs` 并发创建若干资源、proxy key 和 MCP 服务（MCP 用连不上的地址，创建后仍会保存为 `unreachable`），结束后 `GET` 列表和 SQLite 行都要齐全。修复前确认它能稳定复现丢失。
- [x] `AppState` 增加一把管理写锁（`tokio::sync::Mutex<()>`）。改配置的写接口（资源、proxy key、MCP 服务的增删改，token 签发与吊销）在读快照之前拿锁，持有到替换和落库都完成。落库也在锁内，避免内存和数据库的写入顺序不一致。
- [x] 改 catalog 的路径也要排队：工具介绍覆盖（`src/admin/metadata.rs`）、授权后重连（`reconnect_mcp_server`）和后台刷新只在写 catalog 那一步拿锁，请求上游期间不持锁。确认 `swap_config_and_catalog` 携带旧 catalog 的状态时不会丢掉这些写入。
- [x] 在锁的定义处注释它的限制：只串行化本进程；MCP 服务的创建与修改在锁内连接上游，最长会让其他管理写等一个连接超时；多副本由多租户计划改为数据库事务加版本号。
- [x] 同步 [开源版与 SaaS 双形态 · 前置条件](../../../architecture/open-source-and-saas.md#前置条件) 第 1 条、Roadmap [横切：生产就绪](../../../product/roadmap.md#横切生产就绪) 的对应行、`CHANGELOG.md` 的 Fixed 与 `docs/log.md`。

验收：回归测试修复前失败，修复后循环多次都通过；单个写请求的响应和审计记录不变。

## PR2 控制台补回上游 OAuth 授权

- [ ] `write.ts` 的认证选项增加 `oauth`：`grant`（`authorization_code` 或 `client_credentials`）、`client_id`、`client_secret_ref`（只填引用，按 `secret://` 校验）、`scopes`。编辑已有 OAuth 服务时认证默认「保持不变」，原样保存不改认证配置和已存凭据。
- [ ] 服务表格：`oauth.status` 为 `authorization_required` 时显示「授权」，调用 `POST /admin/mcp-servers/{id}/oauth/authorize` 后显示「打开授权页」链接（`target="_blank" rel="noopener noreferrer"`）和有效期。授权 URL 要等请求返回才拿到，这时再 `window.open` 会被浏览器当作弹窗拦截，所以用链接。`authorized` 时显示「撤销授权」，确认后调用 `DELETE /admin/mcp-servers/{id}/oauth`。详情里显示授权状态和 `expires_at`。
- [ ] 授权 URL 带一次性 state，只出现在这个链接里，不写进控制台日志、错误提示或地址栏。
- [ ] Vitest 覆盖表单与请求体的往返。Playwright 用一个指向不可达地址的 `authorization_code` 服务：页面显示「需要授权」和「授权」按钮，点击后出现可读的错误（元数据发现失败）。
- [ ] 改正 [Admin Console](../../../admin/admin-console.md#分阶段路线) C7 的「控制台」一条、Roadmap 支柱一与 Phase 8 的说明、[Gateway Configuration Schema](../../../runtime/config-schema.md) 里授权入口的说明。

验收：`CHANGELOG.md` Unreleased 中「控制台：授权码类 server…」一条描述的行为全部成立；完整的授权流程在 PR7 用真实上游走一遍。

## PR3 控制台收尾

- [ ] 代理密钥表单的服务与工具多选换成 Kumo Combobox（`multiple`），保留现在的过滤，以及「被过滤掉的已选项不丢失」；删掉 `styles.css` 里 `.field select` 的样式和那段说明。[^shell]
- [ ] 删除没有引用的 `web/src/components/pending-page.tsx`。
- [ ] 在 390px 宽度检查表格展开行（MCP 详情、工具调试与介绍、事件详情）。展开内容在跨列单元格里，宽度随整张表，可能要横向滚动才能读完。属实就让展开内容跟随可视区宽度，并在 e2e 的窄屏用例里加断言。

验收：`just check` 通过；`just web e2e` 的窄屏用例覆盖展开行，`.tablewrap` 以外没有横向滚动。

## PR4 中英双语

- [ ] 选定 i18n 库（候选 `i18next` 加 `react-i18next`），写进 `web/README.md` 的「额外依赖」。先确认 Kumo 组件自带的文案（分页、对话框等）怎样本地化。
- [ ] 抽出全部界面文案。语言默认跟随浏览器，可在顶栏切换，选择记在 `localStorage`（读写包 try/catch）。日期与数字用 `Intl` 按当前语言格式化（`web/src/features/format.ts`）。
- [ ] 网关返回的错误码保持原样；界面上的说明文字随语言切换。网关自己输出的 OAuth 回调页（`src/http/oauth_callback.rs`）现在只有中文，改为中英并列。
- [ ] 入口文档英文版：`docs/` 现在只有中文，根目录是 `X.md` 英文、`X.zh-CN.md` 中文。先在 [文档体系约定](../../../engineering/documentation-conventions.md) 定 `docs/` 里英文版的命名与同步规则，再给 [运行网关](../../../admin/running.md) 和 [Gateway Configuration Schema](../../../runtime/config-schema.md) 出英文版。

验收：e2e 在中英两种语言下各走一遍登录和一个读页面；切换语言不丢当前路由和登录状态。

## PR5 K8s 部署物

- [x] 先做 kustomize 清单，不做 Helm chart：`deploy/k8s/` 放网关的 Deployment、Service、PVC、ConfigMap（网关配置），admin token 引用 Secret；控制台的 Deployment 与 Service；另附一份 Ingress 示例。有用户需要参数化时再做 chart。
- [x] 网关固定 1 个副本，在清单里注释原因：存储是 SQLite，限流与配额是进程内状态，多副本要等多租户计划的共享状态。
- [x] 探针用 `/healthz`；容器以非 root 运行，与 `Dockerfile` 一致；镜像标签写发布版本，不用 `latest`。
- [x] [线上部署](../../../admin/deployment.md) 增加 K8s 一节；CI 增加 `kubectl kustomize deploy/k8s` 的渲染检查。

验收：在 kind 集群 apply 后，`/healthz` 通过，控制台能登录并读取页面；删除网关 Pod 后数据仍在。

## PR6 控制台镜像与首个版本

- [x] `release.yml` 同时构建并推送控制台镜像（暂定 `ghcr.io/komiyoo/asterlane-web`），多架构、带版本标签，与网关镜像由同一个 tag 触发；同步 [发布流程 · 产物](../../../engineering/release-process.md#产物)。[^release]
- [x] 提供使用发布镜像的 Compose 写法；README 与中文版的快速上手先写发布产物，从源码构建放到后面。
- [ ] 整理 `CHANGELOG.md` 的 `## [0.1.0]`。打 tag、推 tag、把 GHCR package 改为 Public 由维护者完成，编码代理不推 tag。注意事项见 [发布流程 · 首次发布注意事项](../../../engineering/release-process.md#首次发布注意事项)。

验收：tag 触发后 Release 页有三个平台的二进制，两个镜像都能匿名拉取；在没有源码的机器上按 README 跑通网关和控制台。

## PR7 真实 OAuth 上游验收

- [ ] 选一个公开的、走授权码流程的远程 MCP server，执行前核对它当前的授权方式和是否支持动态客户端注册，记下选择原因。
- [ ] 维护者走一遍：配置 → 需要授权 → 控制台授权 → 代理调用工具 → 重启网关后不需要重新授权 → 撤销后回到需要授权。代理只用 gateway key。
- [ ] 检查响应、控制台、CLI 输出、回调页和日志里没有 token、授权 code 与 client secret。发现的问题先补测试再修。
- [ ] 结论写进 Roadmap Phase 8 的进展与准出，以及 [MCP 协议 · 授权码流程](../../../architecture/mcp-protocol.md#授权码流程管理员一次性授权)。不写账号、client 信息和 token。

验收：Phase 8 准出的第一条成立。

## PR8 贡献者签署方式

- [ ] 维护者在 DCO 与 CLA 之间选定。DCO 只要求提交带 `Signed-off-by`；将来可能更换许可证或另行授权代码时，需要 CLA。
- [ ] 选 DCO：在 `CONTRIBUTING.md` 与中文版写明，CI 检查 PR 提交的 sign-off。选 CLA：选定签署工具并写明流程。
- [ ] 结论写进 Roadmap [产品决策](../../../product/roadmap.md#产品决策) 的「贡献者协议」一行。

验收：新 PR 能自动看出是否满足签署要求。

## Verification

代码改动跑 `just check`；控制台改动另跑 `just web e2e`；纯文档改动只跑 `just docs check`。PR1 的回归测试循环多次确认稳定。PR5 在 kind 集群里演练，PR6 在 tag 触发的真实流水线上验收，PR7 由维护者在真实上游上完成。

全部完成后，对照 [Roadmap · Phase 11](../../../product/roadmap.md#phase-11开源就绪) 的准出逐条确认，再归档本计划。
